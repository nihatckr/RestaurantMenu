# Internationalization Plan — RestaurantMenu

> Confirmed by the 2026-08-27 live-site check: the business runs **tr / en / ru**
> (default **tr**), single currency **TRY**. This decision shapes the `Product` /
> `MenuItem` schema (T2), so it must be settled before the DB model is written.

---

## What must be translatable
- **Product / catalog text:** `title`, `subtitle`, `description`, and the
  legacy `descriptionEn` collapses into this system (no more hard-coded EN field).
- **Category** `name` (and slug stays language-neutral).
- **Static UI chrome:** labels, buttons, error/empty states, alt text.

## What is NOT translated
- **Price** — one currency (TRY); a number/string, not per-language.
- **Slugs** — language-neutral, stable identifiers (routing/keys). Never key
  logic off translated display text (the legacy mistake; AGENTS rule 10 spirit).
- **Images** — shared across languages (one asset per Product).

## Model (recommendation)
Two layers, matching `ARCHITECTURE.md` (Prisma + Postgres, no GraphQL):

1. **Catalog content → per-field translation rows.**
   A `Translation` table keyed by `(entityType, entityId, field, locale) → value`,
   **or** a typed `ProductTranslation` / `CategoryTranslation` child table with
   `(productId, locale, title, subtitle, description)` and a unique
   `(productId, locale)`. **Recommended: typed child tables** — simpler queries,
   type-safe, fits the small fixed field set. Keep the language-neutral facts
   (image, price on MenuItem, drink attributes) on the parent, translatable text
   on the child.

2. **UI chrome → message catalogs.**
   `next-intl` (App-Router-native) message JSON per locale (`tr/en/ru`). No heavy
   framework; this is allowed (small, purpose-built) and does not violate the
   denied-deps list.

## Fallback & resolution
- **Default locale `tr`.** Missing translation for a field → fall back to `tr`,
  never render blank. (Legacy showed both languages at once; the new model shows
  **one** language selected by the user.)
- Locale resolved from the **route** (`/[locale]/[venueSlug]/…`) — matches the
  live SaaS (`/tr`, `/en`, …). Unknown/unsupported locale → default `tr`.
- Store the current locale in the URL (shareable, SSR-friendly), optionally
  persisted in a cookie for the next visit.

## Language switcher

> **Status: BUILT — real `/[locale]` switcher (tr / en / ru).** The menu renders in
> **one language at a time**; the locale is the first path segment (`/tr`, `/en`,
> `/ru`). Switching swaps only that segment, preserving the current venue/category.
> This replaced an earlier "TR+EN shown together + RU toggle" approach (the bilingual
> display and the RU on-demand toggle are gone). See `JOURNEY.md`.

### As built
- **Routing:** every page lives under `src/app/[locale]/…` — the chooser
  (`[locale]/page.tsx`), landing (`[locale]/[venueSlug]/page.tsx`) and category page
  (`[locale]/[venueSlug]/[categorySlug]/page.tsx`), plus `layout/not-found/loading/
  error`. `[locale]/layout.tsx` is the root layout and renders `<html lang={locale}>`
  (so the CSS uppercase gets the right dotted/dotless I per language automatically).
  Unsupported locale → `notFound()` (via `isLocale()`).
- **Static per locale:** the locale is in the URL (not a cookie), so each language is
  a separate static/cacheable route. Data-access reads take `locale` and the `use
  cache` key includes it. `generateStaticParams` prerenders locales × venues ×
  categories (100 pages).
- **Redirect:** `/` → `/tr` (default locale) via `next.config.ts` `redirects()`.
  Canonical, shareable URLs are locale-prefixed; `sitemap.ts` emits them per locale.
- **Switcher UI:** `src/components/LanguageSwitcher.tsx` (client) shows `TR | EN | РУ`
  as real `<Link>`s built from `usePathname()` (swap segment 1), so each choice is a
  static URL that survives reload/share and highlights the active locale
  (`aria-current`).
- **Data:** `localized()` in `src/lib/i18n.ts` returns a single value for the locale
  (tr fallback, never blank). `menu.ts` returns single-language `name`/`title` and a
  localized `tagLabel` for the hard-drink sub-headers (EN via `TAG_EN`; tr/ru fall
  back to the TR tag — there is no RU tag vocabulary yet).
- **Coverage is partial:** categories are fully translated (12/12 tr/en/ru); most
  products only have tr/en, so on `/ru` untranslated items fall back to Turkish
  (never blank) until real RU content lands (owner-blocked U5, see `DATA_SOURCING.md`).

Adding a 4th language later = add it to `LOCALES` (+`LOCALE_LABELS`) and seed the
translations; no per-language code branch.

## Seeding implications (T4)
- Seed must load each Product/Category with its `tr` (required) and any available
  `en`/`ru` translations. Where only Turkish exists, `tr` is the fallback for all.
- The legacy `title` (TR) + `descriptionEn` (EN) map to `tr`/`en` translation
  rows respectively.

## Open questions
- **U-i18n-1** Do all three languages have complete content, or is `tr` the only
  full set (others partial)? Affects how aggressively fallback is used. Resolve
  during data sourcing (`DATA_SOURCING.md`).
- **U-i18n-2** Should drink measure labels (CL/GLASS/BOTTLE) be localized or kept
  as universal abbreviations? (Lean: keep universal.)

## Acceptance (folds into T2/T4/T6–T8)
- Schema separates language-neutral vs translatable fields; `(entity, locale)`
  uniqueness enforced.
- Public pages render one locale with `tr` fallback; language switcher lists only
  data-supported locales; no locale hard-coding.
